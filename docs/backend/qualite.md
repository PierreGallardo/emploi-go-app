# Qualité du backend

Ce guide aide à choisir les tests utiles, à lancer les contrôles du backend et à lire leurs résultats. Les règles à vérifier sont définies dans les guides d'[architecture](architecture.md), d'[API](api.md), de [données](donnees.md) et de [worker](worker.md).

## Choisir les scénarios

Tester les comportements qui engagent une règle ou une garantie. Les scénarios dépendent du changement :

| Sujet                 | Vérifications utiles                                                                                                                                                                            |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Règles métier         | Cas acceptés et refusés, valeurs limites et données absentes, sans conteneur lorsque la règle est indépendante des services.                                                                    |
| API et accès          | JSON, statuts HTTP, validation, session et CSRF. Vérifier les accès autorisés et le refus d'une opération sur une ressource sans droit.                                                         |
| PostgreSQL            | Migrations, requêtes, contraintes, accès concurrents et annulation des écritures en cas d'échec.                                                                                                |
| Redis                 | Expiration, concurrence, saturation, indisponibilité du cache ou des compteurs et reprise après perte d'état.                                                                                   |
| Tâches                | Cohérence entre l'écriture métier et la programmation, exécution par le scheduler du worker (pas seulement l'appel direct de la méthode), interruption, retry et prévention des effets répétés. |
| Emails                | Envoi par l'API hors transaction et sans lock, résultat immédiat, absence de doublon au retry ; rappels envoyés par le worker.                                                                  |
| Fournisseurs externes | Réponse de succès, dépassement du timeout, réponse lente, échec et retries autorisés, avec un délai réduit en test. Un mock qui renvoie toujours un succès ne suffit pas.                       |

En CI, vérifier les intégrations avec des mocks ou des services simulés, sans contacter un fournisseur réel ni utiliser de secret de production. Les tests navigateur couvrent le raccordement et les parcours essentiels ; ils ne remplacent pas les tests des règles backend.

## Principes

Ces principes valent pour tous les tests du dépôt. Le [guide frontend](../frontend/qualite.md#principes) les applique à Vitest, Testing Library et Playwright. Ils suivent la [pyramide des tests](https://martinfowler.com/articles/practical-test-pyramid.html) et les [recommandations de test de Spring Boot](https://docs.spring.io/spring-boot/reference/testing/index.html).

- **Un comportement par test.** Le nom dit l'action et le résultat attendu. Un test qui échoue désigne ainsi la règle cassée.
- **Aucune logique dans un test.** Ni `if` ni boucle : une assertion conditionnelle peut ne jamais s'exécuter. Plusieurs cas se décrivent par un test paramétré, avec un libellé par cas.
- **Assertions précises.** Vérifier les valeurs exactes, pas seulement l'absence d'erreur. Préférer les assertions qui affichent la valeur obtenue : comparer avec `assertThat(a.equals(b)).isTrue()` n'affiche que `false` en cas d'échec. Ne pas copier en dur une valeur issue des données (nombre de lignes, version de migration) : la lire depuis sa source ou comparer l'état avant et après.
- **Déterminisme.** Injecter l'horloge, tokens de test compris, et toute source d'aléa. Ne jamais attendre une durée fixe : attendre une condition, avec un timeout. Un test ne modifie pas l'état global de la JVM, comme la locale par défaut : l'indépendance à la locale se vérifie dans une exécution Surefire dédiée, dont la JVM est en turc (`locale-tr`, `AccountIdentifierTest`, ignorée ailleurs ; `./mvnw test` l'exécute, `-Dtest` ne la lance pas dans l'exécution par défaut).
- **Le bon niveau, sans doublon.** Vérifier un comportement au niveau le plus bas qui le prouve : règle métier sans conteneur, JSON, statuts, droits et CSRF avec MockMvc, transactions, SQL et Redis en intégration, navigateur pour ce que lui seul voit. Ne pas répéter le même comportement à un autre niveau.
- **Vrais objets d'abord.** Un mock est réservé à un service externe (fournisseur d'emails, Google) ou à une source non déterministe (horloge, aléa). Un mock qui répond toujours par un succès ne prouve rien : il simule aussi les délais dépassés et les échecs.

## Organisation des tests

Les noms, packages et emplacements suivent les [conventions Java](conventions.md#noms-et-emplacement).

| Type de test                                      | Outils et exécution                                                                                                                                                        | Rapports                           |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Tests unitaires, HTTP et d'architecture (`*Test`) | JUnit Jupiter, MockMvc avec la configuration de sécurité, ArchUnit. Maven Surefire les exécute pendant `test`, dans une exécution par défaut et une exécution `locale-tr`. | `backend/target/surefire-reports/` |
| Tests d'intégration (`*IT`)                       | PostgreSQL et Redis réels dans Testcontainers, avec des ressources temporaires. Maven Failsafe les exécute pendant `verify`. Docker doit fonctionner.                      | `backend/target/failsafe-reports/` |

Les conteneurs de test restent séparés des services de développement. Une indisponibilité de Docker fait échouer les tests qui en dépendent ; ils ne sont pas ignorés automatiquement.

### Portes de test

Chaque domaine offre aux tests des autres domaines une porte de test, nommée `<Domaine>TestSupport`. Elle se trouve dans le package `application` du domaine, sous `src/test`. Par exemple, `AuthenticationTestSupport` crée un compte connecté.

Les tests d'un domaine passent par la porte d'un autre domaine, jamais par ses classes internes. Un changement interne ne doit pas casser les tests des autres domaines.

La boîte à outils commune `fr.emploigo.support` ne contient que des outils partagés par tous les domaines : conteneurs, horloge, navigateur, faux fournisseurs. Elle n'importe d'un domaine que sa porte de test. Un besoin propre à un domaine passe par cette porte.

### Support des tests d'intégration

Les classes `*IT` de l'API étendent `IntegrationTest`, dans [`fr.emploigo.support`](../../backend/src/test/java/fr/emploigo/support/). Les `*IT` du domaine `auth` étendent `AuthenticationIntegrationTest`, dans son package `application`, qui ajoute les beans d'authentification. Les spies d'authentification sont déclarés une seule fois, par `@AuthenticationTestDoubles` sur `IntegrationTest` : tous les tests partagent ainsi un seul contexte Spring. Ce support évite de recopier les conteneurs, l'horloge, le client HTTP et les faux serveurs :

| Besoin                | Support                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| PostgreSQL et Redis   | `Containers` : un conteneur de chaque par exécution Maven. PostgreSQL passe par `@ServiceConnection`. Redis est branché par propriétés, car la connexion de conteneur de Spring Boot n'a pas de mot de passe : il reste protégé par mot de passe, comme en production.                                                                                                                                                   |
| Horloge               | `TestClock`, un seul bean `@Primary`, remis à l'heure réelle avant chaque test. Les tokens d'identité de `FakeGoogle` sont datés par cette horloge, que l'application utilise aussi pour les valider.                                                                                                                                                                                                                    |
| Client HTTP           | `Browser` : cookies d'un navigateur et token CSRF. Il refuse tout `Set-Cookie` sans préfixe `__Host-`, sans `Secure`, hors `Path=/` ou avec `Domain` (`HostCookies`).                                                                                                                                                                                                                                                    |
| CSRF avec MockMvc     | `CsrfTokens` : token valide ou falsifié, en cookie et en header comme un navigateur. Le `csrf()` de `spring-security-test` n'est pas utilisé : il remplace le dépôt de tokens que tous les tests du contexte partagent.                                                                                                                                                                                                  |
| Fournisseurs externes | `FakeProviders` : emails (`/emails`) et `FakeGoogle`, sur un seul serveur local. Le statut renvoyé se choisit, les appels se comptent, et `Stall` retient une réponse (au plus 5 s) pour simuler un fournisseur lent ou une requête en cours.                                                                                                                                                                            |
| Compteurs et attentes | `MailCounters` : appels au fournisseur d'emails et messages distincts depuis sa création, relatifs au scénario. `IntegrationTest` fournit aussi `count`, `code`, `flag` et `overlappingAtTheRow` (deux appels qui se croisent derrière une ligne tenue par le test, quand l'ordre d'arrivée importe peu). `AuthenticationIntegrationTest` fournit `permitNextMail` (délai d'attente entre deux emails levé sans dormir). |
| Lock de ligne         | `RowLock`, à utiliser dans un `try-with-resources` : une connexion du test tient le lock d'une ligne jusqu'à `commit()` ou `release()`, et `awaitWaiters` attend que des transactions de l'application s'y bloquent, sans dormir ; il compte les attentes de toute la base. `AdvisoryLock` tient de même un lock consultatif, et son `awaitWaiters` ne compte que les attentes de sa clé.                                |
| Logs émis             | `LogCapture`, à utiliser dans un `try-with-resources` : collecte les événements d'une classe, sans lire la console ; l'appender est retiré même si le test échoue.                                                                                                                                                                                                                                                       |
| Échec SQL provoqué    | `SqlFailure`, à utiliser dans un `try-with-resources` : le déclencheur est supprimé même si le test échoue.                                                                                                                                                                                                                                                                                                              |
| Panne Redis           | `Containers.pauseRedis()` et `Containers.fillRedisMemory()` (mémoire pleine), aussi dans un `try-with-resources` : la reprise est garantie, et `IntegrationTest` reprend un Redis resté en pause ou limité. `DEBUG RESTART` relance le serveur avec un autre `run_id`, dans le conteneur de test seulement.                                                                                                              |
| Session authentifiée  | `AuthenticationTestSupport`, porte de test du module `auth` (voir [portes de test](#portes-de-test)) : crée un compte connecté et remet à zéro les beans d'authentification entre deux tests. ArchUnit n'examine pas les tests : cette frontière est une convention.                                                                                                                                                     |

Avant chaque test, `IntegrationTest` vide les tables de l'application et remet à zéro les beans d'authentification par `AuthenticationTestSupport`, qui réinitialise aussi les spies. Puis il vide Redis (en y laissant le témoin des compteurs, pour qu'aucun test ne signale une perte qu'il n'a pas provoquée), remet l'horloge et les faux serveurs à zéro. Un test ne dépend donc ni de l'ordre d'exécution ni des données d'un autre test, et aucune classe n'utilise `@DirtiesContext`. Le nettoyage attend un lock PostgreSQL au plus 15 s, puis échoue avec « Nettoyage bloqué par un lock » au lieu de se bloquer. Il attend de la même façon un Redis qui ne répond pas (calage du disque ou du processeur d'un runner, au-delà des 500 ms du client) : le vidage et le témoin sont réessayés 15 s au plus, puis le test échoue avec la dernière erreur. `Containers.stallRedis(Duration)` bloque Redis pour le reproduire (`IntegrationTestPreparationIT`). Les tests du worker (`WorkerInfrastructureIT`, les `*IT` de l'import des établissements) partagent le même PostgreSQL mais n'étendent pas `IntegrationTest` : ils portent `@WorkerTest`, qui leur donne un seul contexte (profil `worker`, Redis absent, API Sirene sur un port local fermé), et vident eux-mêmes les tables avant chaque test. Le nettoyage garde les données de référence du schéma `reference` et les tables de PostGIS. Leur scheduler ne cherche les tâches qu'une fois par heure, la purge n'y est due que cinq minutes après chaque exécution, et l'import des établissements qu'à son heure quotidienne : le contexte, gardé en cache pour les autres tests, ne modifie pas la base pendant qu'ils tournent. Un test lui demande une exécution quand il en a besoin.

Pour vérifier qu'aucun test ne dépend de l'ordre, lancer les tests d'intégration seuls dans un ordre aléatoire à seed fixé, depuis `backend/` (Docker requis) :

```bash
rm -rf target/failsafe-reports
./mvnw -ntp process-test-classes failsafe:integration-test failsafe:verify \
  -Djunit.jupiter.testmethod.order.default='org.junit.jupiter.api.MethodOrderer$Random' \
  -Djunit.jupiter.testclass.order.default='org.junit.jupiter.api.ClassOrderer$Random' \
  -Djunit.jupiter.execution.order.random.seed=1
```

Ne pas passer ces propriétés à `verify` : elles s'appliquent aussi à surefire et mélangeraient alors les tests unitaires, ce que cette vérification ne vise pas. Le seed utilisé figure dans chaque rapport `target/failsafe-reports/TEST-*.xml` (propriété `junit.jupiter.execution.order.random.seed`) : la vérifier avant de conclure, et relancer avec le même seed pour rejouer un échec.

Peu de configurations Spring distinctes : chacune garde son contexte, donc son pool de connexions, en cache. Les tests d'API partagent un contexte. Seuls changent celui du profil `production`, celui du worker, qui n'a pas de Redis, et celui de `ProviderTimeoutIT`, qui réduit les timeouts de réponse des fournisseurs : un client HTTP fixe son timeout à sa construction. Avant d'ajouter un `@MockitoBean`, un `@MockitoSpyBean`, une propriété ou un profil à une seule classe, vérifier que le gain justifie un contexte de plus.

## Frontières d'architecture

ArchUnit examine les classes Java compilées, selon son [guide utilisateur](https://www.archunit.org/userguide/html/000_Index.html). Sa version est fixée dans le [POM](../../backend/pom.xml). Il est utilisé depuis JUnit Jupiter comme dépendance de test ; le backend n'ajoute pas de composant Spring Modulith à l'exécution.

Les règles ArchUnit traduisent le [guide architecture](architecture.md#dépendances-à-respecter) :

- Placement des classes et dépendances entre `api`, `application`, `domain` et `infrastructure`.
- Indépendance de la configuration commune.
- Entrées publiques et absence de cycles entre domaines.
- Accès aux bibliothèques techniques explicitement couvertes par les règles.
- Rôle de chaque composant (`@ApiOnly`, `@WorkerOnly` ou `@ApiAndWorker`, jamais un `@Profile` qui nomme le worker), composants des packages `api` réservés à l'API, et composants partagés ou du worker sans ressource de l'API (Redis, sessions, contrôleurs, classes `@ApiOnly`). Ces trois règles ne sont pas dans la liste commune : leurs exemples n'ont aucun composant.

Quatre autres règles s'appliquent à tous les domaines :

- `domain` ne dépend d'aucun type de persistance, annotations comprises.
- `application` ne dépend ni d'`infrastructure`, ni de Spring Data, ni de JPA.
- `@Entity` n'apparaît que dans `infrastructure`, sur des classes nommées `…JpaEntity`.
- Les noms évitent les mots interdits et le préfixe `I`. Les suffixes `Controller`, `Configuration`, `Properties` et `Exception` suivent le type ou l'annotation. Le suffixe `UseCase` n'est vérifié que pour sa couche.

La règle `subjectsOfADomainAreFreeOfCycles` refuse tout cycle entre les sujets d'un même domaine, un sujet étant un sous-package `<couche>.<sujet>` pris dans toutes ses couches ensemble. Les classes posées directement dans une couche n'appartiennent à aucun sujet.

Une règle sépare aussi les échecs des use cases de ceux des adaptateurs : aucune classe d'`infrastructure`, de n'importe quel domaine, n'appelle un constructeur d'une exception de `application`, ni une méthode statique de cette couche qui rend une telle exception (`AuthenticationFailedException.invalidCredentials()`). Elle n'a pas de liste de classes : une classe nouvelle est contrôlée sans autre geste. Un `catch` n'est pas visé (`AuthenticationSessionFilter`), ni une exception de `domain`. Limites : elle ne suit ni une exception créée par réflexion, ni une référence de constructeur (`GoogleAuthenticationFailedException::new`), ni une exception rendue par une méthode d'instance. Elle ne retient pas non plus les `catch` : un adaptateur peut attraper une exception d'`application` sans la lancer.

Deux contrôles lisent les sources, car un SQL est une constante que le code compilé ne montre pas (`AccountTableAccessTest`) : seuls les fichiers du package `auth/infrastructure/account` nomment la table `auth_accounts`, et aucun SQL ne répète le rôle `'JEUNE'`, qui définit qui peut s'authentifier (`Account.mayAuthenticate()`). Ils échouent aussi si les sources ne sont pas lues ; des fichiers de test prouvent qu'ils détectent une infraction. Les autorisations de route (`hasRole("JEUNE")`) ne sont pas visées. Limites : ils lisent les fichiers Java de `src/main/java`, sans tenir compte de la casse ; un nom coupé par une concaténation, ou un SQL placé dans `src/main/resources`, leur échappe, et la revue reste nécessaire.

D'autres règles nomment des classes de l'application, dont deux sur les transactions. La première interdit à toute méthode transactionnelle, annotée ou dans une classe annotée, d'atteindre `QuotaEnforcer` ou Redis (une classe qui en dépend, ou une interface qu'une telle classe implémente) par les appels du code analysé ; elle ne suit ni une référence de méthode ni un constructeur, ni un `@Transactional` hérité ou posé par méta-annotation, et ne couvre pas les autres appels réseau (Resend, Google). La seconde vérifie que `ResumeSessionUseCase.resume`, `AuthenticationSessions.revoke` et `ReconnectionRevoker.revoke` ne sont pas transactionnelles. La revue reste nécessaire pour ces cas.

Les classes de test sont exclues de l'analyse du code de production. Un domaine peut ne pas avoir toutes les couches, sauf `auth` et `establishment` : `BackendArchitectureTest` liste leurs quatre couches et échoue si l'une n'a plus de classe (un package renommé aussi). En revanche, une règle ne passe jamais à vide : elle échoue si elle ne contrôle aucune classe, c'est-à-dire si le code analysé est vide ou si une couche qu'elle cite n'existe dans aucun domaine. Les exemples autorisés et interdits vérifient aussi les règles elles-mêmes : les conserver lors d'une évolution pour détecter un contrôle qui accepterait toutes les dépendances.

**Un contrôle de dépendances ne prouve pas les droits métier, le chargement JPA, la cohérence transactionnelle ou la sûreté d'un retry.** La revue examine aussi les responsabilités, les nouveaux SDK, la réflexion, les références dans la configuration et le SQL sous forme de texte. Actualiser les bibliothèques couvertes lorsqu'une dépendance technique est ajoutée.

## Vérifier une modification

Depuis la racine du dépôt :

| Commande                    | Portée                                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `npm test -- backend`       | Maven `test` : tests HTTP, unitaires et d'architecture, sans conteneurs.                                    |
| `npm run check -- backend`  | Maven `verify`, dont les tests avec PostgreSQL et Redis temporaires.                                        |
| `npm run check -- contract` | Comparaison du contrat OpenAPI et des types frontend avec une API isolée construite depuis le code courant. |
| `npm run check`             | Contrat, formatage, lint, types, tests des scripts et du frontend, compilation frontend et Maven `verify`.  |
| `npm run test:e2e`          | Parcours Chromium avec le frontend construit, une API et des services temporaires.                          |

- Docker doit fonctionner pour les intégrations, le contrat isolé et les tests navigateur.
- Les contrôles Maven utilisent `backend/target/`, distinct de `backend/target-dev/` pour la session de développement et de `backend/target-isolated/` pour le contrat et les E2E. Ils peuvent s'exécuter pendant cette session.
- Une commande npm qui trouve `backend/target/` occupé par une autre attend son tour.

Pour un lancement direct depuis `backend/` :

| Commande         | Effet                                         |
| ---------------- | --------------------------------------------- |
| `./mvnw test`    | Exécuter les tests Surefire.                  |
| `./mvnw package` | Exécuter Surefire, puis construire le JAR.    |
| `./mvnw verify`  | Ajouter les tests Failsafe à la construction. |

Sous Windows, utiliser `mvnw.cmd`. Les commandes Maven directes ne prennent pas le lock des scripts npm : ne pas les lancer pendant `npm test` ou `npm run check`, qui compilent la même sortie.

## Avant une contribution

1. Exécuter les vérifications adaptées au changement final, selon [CONTRIBUTING](../../CONTRIBUTING.md#vérifications-locales). Pour du texte ou des templates seuls, relire les liens, exemples et le formatage suffit.
2. Inclure les fichiers générés lorsque le contrat évolue et les migrations lorsque le schéma change.
3. Relire les effets sur les droits, transactions, tâches et configurations ; actualiser les guides concernés.
4. Indiquer dans la PR les vérifications exécutées et leurs résultats, ainsi que les contrôles importants non réalisés.

Le [guide CI](../ci.md) décrit les contrôles GitHub Actions, leurs rapports et la lecture des échecs. Une réussite locale ne dispense pas du résultat des contrôles sur le commit proposé.
